# NovaBoost — технический проект

**Цель:** сделать самостоятельный клиентский набор оптимизаций для Fabric 1.21.11, который измеримо уменьшает лишнюю работу рендера и сглаживает скачки времени кадра на слабых и старых компьютерах. Это проект поэтапной разработки, а не обещание заменить Sodium одной короткой версией.

## 1. Что именно строим

NovaBoost состоит из независимых модулей. Каждый модуль можно отключить отдельно, а ошибка или нехватка данных в одном модуле не должна ломать Minecraft.

| Подсистема | Задача | Состояние |
| --- | --- | --- |
| Core / Config | Настройки, профили, ограничения CPU и памяти | 0.1.0: базовая конфигурация |
| Entity Visibility | Не отправлять на рендер невидимые сущности за непрозрачными блоками | 0.1.0: синхронные проверки с лимитом |
| Block Entity Visibility | Аналогичная работа для сундуков, механизмов и других block entities | Планируется; по умолчанию выключено |
| Chunk Scheduler | Умнее распределять перестроение секций и загрузку GPU-буферов | Планируется |
| Particle Budget | Снижать лишнюю стоимость визуальных частиц, не менять симуляцию | Планируется |
| Memory / Cache | Ограниченные кеши и сокращение повторных вычислений | Планируется |
| Diagnostics | Локальные замеры времени кадра, очередей, кешей и пропусков | Планируется |
| Launcher Bridge | Установка, проверка версии, включение и отключение мода в профиле | Начальная интеграция в NovaCraft |

### Не является целью

- Клиентский мод не может поднять TPS удалённого сервера. Он может уменьшить локальную цену отрисовки большого количества сущностей, частиц и block entities.
- Не обещается фиксированный множитель FPS. Результат зависит от того, упирается ли компьютер в CPU, GPU, память или загрузку чанков.
- В базовой версии нет обязательной замены графического движка, Vulkan, новых OpenGL-функций или обязательных шейдеров.
- Мод не меняет реестр Windows, драйверы, системные службы, автозагрузку и файлы сервера.
- Существующие моды не переименовываются и не выдаются за код NovaBoost.

## 2. Главные инженерные правила

1. **Fail open:** неизвестная видимость означает «отрисовать», а не «скрыть».
2. **Ограниченная работа:** каждый алгоритм имеет лимит операций, размер очереди, памяти и время выполнения.
3. **Никакого доступа к миру из фонового потока:** worker-потоки получают только неизменяемые снимки данных, подготовленные на клиентском потоке.
4. **Изоляция модулей:** ошибка отдельного оптимизатора отключает его и записывается в локальный лог; она не должна ломать весь клиент.
5. **Минимум Mixin-инъекций:** сначала ищем подходящий Fabric API event; Mixin используем только там, где API не позволяет безопасно решить задачу.
6. **Измерения прежде обещаний:** включение функции не считается улучшением, пока сравнительный тест не подтвердил выигрыш.
7. **Совместимость важнее агрессии:** если модифицированная сущность, блок или рендерер не распознаны, пропускаем оптимизацию.

## 3. Архитектура модулей

### 3.1 Core

Пакет `core` отвечает за конфигурацию и общие ограничения:

- загрузка конфигурации с проверкой диапазонов;
- режимы `Low-end`, `Balanced`, `Compatibility` и `Custom`;
- общий бюджет времени и операций для необязательных оптимизаций;
- версия схемы конфигурации и безопасная миграция старых файлов;
- единый реестр состояния модулей: включён, временно приостановлен, отключён из-за ошибки.

Режимы не должны автоматически менять дальность прорисовки, разрешение, настройки Windows или JVM-аргументы. Они управляют только поведением NovaBoost.

### 3.2 Entity Visibility

**Текущая основа 0.1.0:** перед возвратом результата `EntityRenderDispatcher.shouldRender` проверяются три точки ограничивающего параллелепипеда. Объект скрывается, только если все три луча встретили блок, который считается перекрывающим. Ответ кешируется на короткое время, а число лучей ограничено на игровой тик.

**Известные ограничения 0.1.0:**

- проверки выполняются синхронно на клиентском потоке;
- кеш на несколько тиков может устареть, если камера или сущность быстро переместилась;
- `canOcclude` — консервативный фильтр, но он не описывает все особенности кастомных форм блоков;
- при плотной сцене бюджет лучей быстро закончится, и оптимизация просто перестанет скрывать новые объекты;
- эта версия не измеряет реальный выигрыш FPS.

**Версия 0.2 — исправление корректности кеша:**

- кешировать поколение мира, ID и UUID сущности, позицию сущности и позицию камеры на момент проверки;
- инвалидировать результат при смене измерения, удалении сущности, существенном движении камеры или цели;
- заменить полную очистку кеша на ограниченное вытеснение старых записей;
- добавить whitelist/blacklist по EntityType и безопасный общий выключатель;
- добавить счётчики: кандидаты, видимые, скрытые, кеш-попадания, промахи, израсходованные проверки.

**Версия 0.3 — асинхронный путь:**

1. Клиентский поток собирает ограниченный снимок только уже загруженных блоков вокруг кандидатов.
2. Снимок содержит простые неизменяемые данные о перекрытиях; ссылки на `Level`, `BlockState`, `Entity` и другие изменяемые игровые объекты не передаются worker-потокам.
3. Фоновая задача проверяет лучи только по этому снимку и возвращает результат вместе с номером поколения.
4. Клиентский поток принимает результат лишь если мир, сущность, камера и снимок всё ещё актуальны.
5. При переполнении очереди, просроченном результате или неполном снимке сущность рисуется обычным способом.

Worker-пулы должны быть маленькими и ограниченными. Нельзя запускать новый поток на каждую сущность или позволять очереди расти без лимита.

**Исключения из culling по умолчанию:** игроки и аватары, светящиеся, именованные, пассажиры и транспорт, сущности с кастомным поведением/рендером, а также объекты ближе минимальной дистанции. Для модпаков должен быть общий whitelist.

### 3.3 Block Entity Visibility

Это отдельный этап после стабилизации Entity Visibility.

Block entities могут иметь рендер за пределами своего блока: большие механизмы, лучи, модели Create-подобных модов, нестандартные сундуки. Нельзя считать, что видимая область равна одному блоку.

Порядок реализации:

- начать с выключенной по умолчанию функции;
- использовать фактические границы рендера, если рендерер их предоставляет;
- включить whitelist по типам и namespace модов;
- не отсекать неизвестные и нестандартные рендереры;
- добавить тестовые сцены с beacon, сундуками, механизмами и модовыми block entities;
- включать по умолчанию только после проверки совместимости и измерений.

### 3.4 Chunk Scheduler

Здесь потенциально находится более крупный выигрыш для сцен с быстрым перемещением и большим количеством модовых чанков. Но это и самая рискованная часть.

**Этап 1 — планировщик поверх штатного рендера:**

- дедупликация повторных запросов на перестроение секции;
- приоритет по близости к камере, видимости и причине перестроения;
- ограниченный бюджет отправки готовых буферов на GPU за кадр;
- отмена устаревших задач после смены мира или выгрузки секции;
- не задерживать срочные перестроения возле игрока ради дальних секций.

**Этап 2 — профилирование компиляции:**

- отдельно измерять время подготовки геометрии, ожидания worker-пула и загрузки буферов;
- отслеживать очередь, среднее время ожидания и число отмен;
- не увеличивать число потоков автоматически без замеров CPU и памяти.

**Этап 3 — собственный движок секций, только если этапы 1–2 докажут необходимость:**

- снимок блока и соседних состояний;
- извлечение граней и occlusion graph;
- компиляция отдельных render layers;
- region-based GPU buffers;
- ограниченная загрузка и освобождение буферов;
- прозрачность, block entities, resource packs, shaders и API-совместимость.

Это отдельный большой проект. Нельзя объявлять NovaBoost «аналогом Sodium», пока не реализованы и не протестированы компилятор секций, хранилище геометрии, планирование GPU upload и совместимые render passes.

### 3.5 Particle Budget

Управляет только визуальной стоимостью частиц на клиенте:

- настройка плотности визуальных частиц;
- ограничение декоративных частиц при перегрузке кадра;
- сохранение симуляции мира и серверных событий;
- исключения для важных эффектов попадания/состояния и для частиц, помеченных модом как критические;
- режим Compatibility по умолчанию не вмешивается в неизвестные пользовательские частицы.

Нельзя заменять это пропуском игровых тиков или изменением логики сущностей.

### 3.6 Memory / Cache

- все кеши имеют явный предел по элементам и/или байтам;
- кеши очищаются при смене мира, resource reload и выгрузке соответствующих данных;
- запрещены принудительные вызовы `System.gc()`;
- не хранить сильные ссылки на выгруженные сущности, чанки или текстуры;
- избегать копирования больших массивов на каждом кадре;
- проверять allocation rate и heap usage отдельно от FPS.

### 3.7 Diagnostics

Локальная диагностическая панель должна показывать:

- frame time p50 / p95 / p99, а не только средний FPS;
- число объектов-кандидатов, реально отсечённых и пропущенных из-за бюджета;
- размер кешей и число вытеснений;
- очередь и задержку задач chunk scheduler;
- объём памяти и частоту GC, если данные доступны без опасных или платформенно-зависимых трюков;
- предупреждение, когда оптимизация сама потребляет больше времени, чем экономит.

Диагностика локальная. Сетевой телеметрии и отправки статистики нет.

## 4. Аппаратные профили

| Профиль | Назначение | Поведение |
| --- | --- | --- |
| Low-end | Старые GPU и слабые CPU | Минимальная стоимость проверок, низкие лимиты очередей, без собственного графического движка |
| Balanced | Обычные компьютеры | Умеренный culling и планирование чанков |
| Compatibility | Большие модпаки и неизвестные рендереры | Только проверенные безопасные функции; неизвестные типы пропускаются |
| Custom | Ручная настройка | Пользователь меняет лимиты отдельных модулей |

Для Radeon HD 6900 нельзя считать Sodium гарантированно совместимым: официальная страница Sodium указывает AMD Radeon HD 7000 (GCN 1) или новее как поддерживаемую базовую линейку; более старые карты находятся вне этой базовой гарантии. Это не доказывает, что Sodium обязательно не запустится, но требует отдельной проверки. NovaBoost не должен требовать современного рендер-бэкенда без проверки возможностей устройства.

## 5. Совместимость с модпаками и серверами

- NovaBoost остаётся клиентским модом и не требует установки на удалённый сервер.
- Никаких изменений пакетов, поведения мобов, физики или серверных тиков.
- Неизвестные EntityType и block entities по умолчанию не подвергаются агрессивному culling.
- Mixin-инъекции фиксируются по версии Minecraft и покрываются проверками загрузки.
- После resource reload кеши рендер-состояний очищаются.
- Конфликты с другими culling/render модами должны диагностироваться отдельно; нельзя молча включать две конкурирующие замены одного участка рендера.

## 6. Тестирование и измерение

### Автоматические проверки

- unit-тесты бюджета, кеша, срока жизни записей и инвалидации;
- тесты конфигурации: неправильные значения, отсутствующий файл, миграция;
- проверка metadata: mod ID, Minecraft, Loader, Java, client environment;
- проверка структуры JAR, Mixin-конфигурации и SHA-256;
- проверка, что worker-поток не обращается к игровому миру;
- smoke-test запуска клиента Fabric для каждой поддерживаемой сборки, когда это можно стабильно выполнить в CI.

### Сценарии ручного бенчмарка

1. Обычная местность, минимум сущностей.
2. Толпа мобов и игроков, часть за стенами.
3. База с большим количеством block entities.
4. Быстрое перемещение и генерация/загрузка чанков.
5. Тяжёлый модпак на удалённом сервере.
6. Обычный инвентарь и меню — чтобы увидеть, не ухудшили ли мы GUI.

Для каждого сравнения фиксировать Minecraft, Loader, модпак, seed/мир, дальность прорисовки, разрешение, настройки графики и драйвер. После прогрева сделать три одинаковых прогона и сравнить медиану.

Основные показатели: p50/p95/p99 времени кадра, 1% low, загрузка CPU/GPU, память и число GC. Средний FPS отдельно недостаточен. Функция остаётся выключенной по умолчанию, если она не даёт повторяемого выигрыша или вызывает заметные артефакты.

## 8. Критерии готовности

Мод не объявляется готовым только потому, что JAR собрался. Для релиза требуются:

- успешная сборка и unit-тесты;
- проверка metadata и целостности JAR;
- реальный запуск Minecraft 1.21.11 + Fabric;
- ручная проверка сцен с большим количеством сущностей;
- отсутствие пропадающих игроков и важных именованных/светящихся объектов;
- измерения «до/после» на одном и том же компьютере;
- changelog с перечислением реально реализованных оптимизаций и известных ограничений.

## 9. Технические ориентиры

- Fabric API events предпочтительнее широких Mixin-вмешательств.
- Render extraction и drawing — разные стадии; подготовка данных должна отделяться от отрисовки.
- Для фоновых задач используются только неизменяемые снимки данных.
- Не копировать код Sodium или Entity Culling. Использовать только собственные реализации и публичные API с соблюдением лицензий.
- Любая новая оптимизация сначала проходит тест на совместимость, затем бенчмарк.
